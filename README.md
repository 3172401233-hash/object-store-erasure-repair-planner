# object-store-erasure-repair-planner

纠删码对象修复规划器：在磁盘批量故障场景下，判断对象是否仍可读、
计算缺失分片与修复优先级，并在带宽和源节点读取流约束下生成分轮修复计划。

## 存储访问均为本地模拟

本项目**不包含任何真实存储、磁盘或网络访问**。所有节点位置（`node_id`）、
分片状态、校验摘要、带宽和节点负载都是入参中给出的内存数据：

- 规划器只做"纸面"调度，不会读取磁盘、发起 RPC 或写回数据；
- 重建后的分片只体现在输出计划里（目标节点沿用原分片位置），不做真实落盘；
- 校验通过与否由 `Shard.checksum` 与 `Shard.expected_checksum` 比对得出，
  摘要本身也是模拟字符串。

## 核心规则

- 编码参数为数据分片 `k`、校验分片 `m`，共 `k+m` 个分片，分片不共置节点。
- 对象可读/可恢复条件：有效分片数 `>= k`；低于 `k` 即超过容错阈值。
- 分片状态有三种：`AVAILABLE`（可用）、`MISSING`（磁盘故障丢失）、
  `CORRUPT`（校验失败）。校验失败的分片禁止作为修复源，且自身需要重建。
- 单分片大小按 `ceil(对象大小 / k)` 模拟；重建一个分片需读取 `k` 个有效源
  分片并写出 1 个新分片，单任务带宽为 `(k+1) * 单分片大小`。
- 每轮调度同时受两条约束：
  - 修复带宽不得超过 `max_bandwidth_bytes`；
  - 每个源节点每轮提供的分片读取流不得超过 `max_node_streams`，避免批量
    故障时健康节点被修复流量打满、拖慢正常读取。
- 同一对象同一分片只进入一次计划，不会重复修复；受约束未调度的分片
  推迟到下一轮，最终仍无法调度时在跳过记录中给出原因。

## 修复优先级

不只按丢失数量排序（避免先修低价值小对象），而是综合风险与热度：

- 风险分 `risk = min(1, 缺失分片数 / m)`：越接近容错阈值越危险，
  冗余耗尽（恰好还能恢复）的对象排在最前；
- 热度分 `heat_score = 对象热度 / 批次最大热度`；
- 总分 `priority = 0.7 * risk + 0.3 * heat_score`，权重可在构造器调整；
- 同分时依次按原始热度、对象大小、对象 ID 决定顺序，保证输出稳定。

跳过原因（`SkipReason`）：

- `INSUFFICIENT_SOURCES`：有效分片不足 `k`，对象不可恢复；
- `NODE_OVERLOADED`：源节点读取流达到上限，推迟到后续轮次；
- `BANDWIDTH_EXHAUSTED`：本轮剩余带宽不足以容纳重建任务。

## 输出结构

`RepairPlanner.plan()` 返回 `RepairPlan`：

- `repair_order`：`(对象 ID, 分片编号)` 的修复顺序；`object_order` 为对象级顺序；
- `rounds`：每轮的任务列表、`bandwidth_bytes`（每轮带宽）和
  `node_load`（各源节点读取流负载）及当轮跳过记录；
- `object_status`：每个对象的可读性、缺失数、有效数、风险/热度分与优先级；
- `unrecoverable`：仍不可恢复的对象及中文原因；
- `final_skipped`：最终未安排的分片及跳过原因；
- `total_bandwidth_bytes`、`final_node_load`：累计带宽与累计节点负载。

## 运行环境与测试

代码面向 Python 3.8.2，仅使用标准库（`dataclasses`、`enum`、`typing`）。

```bash
python -m unittest
```

测试覆盖：刚好可恢复（仅剩 k 个有效分片）、超过容错阈值、热点对象优先级、
源节点过载推迟、校验失败分片排除、批量修复的带宽分轮与去重。

本地模拟演示：

```bash
python demo.py
```
